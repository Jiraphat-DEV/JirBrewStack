# 09 · ตัวตรวจ ruleset

กลุ่ม: Rules · ต้องรอ: ไม่ต้องรออะไร · ประมาณ 1 วัน
[กลับไป roadmap](../2026-08-05-jirbrewstack-v2.1-roadmap.md)

## ปัญหา

ตอนนี้การตรวจว่า `brewing-rules.js` เขียนถูกรูปหรือไม่ อยู่ในเทส 16 ของ `brew.test.js` ซึ่งรันตอน CI เท่านั้น พอ ruleset ย้ายขึ้น Firestore (item 10) และแก้ได้จากในแอป (item 12) การตรวจต้องรันได้ 3 ที่: ในเทสเหมือนเดิม, ในเบราว์เซอร์ตอนกำลังแก้, และใน Cloud Function ตอนจะเขียนทับ

**ถ้าตรวจคนละแบบกัน 3 ที่ ก็เท่ากับไม่ได้ตรวจ** ต้องเป็นฟังก์ชันเดียวกันตัวเดียว

item นี้เป็นด่านเดียวที่กันไม่ให้ ruleset ที่เขียนผิดไปพังแอปพร้อมกันทุกคน

## ต้องได้อะไร

1. ฟังก์ชัน `validateRuleset(ruleset)` แยกออกมาเป็นไฟล์ของตัวเอง **คืนรายการปัญหา ไม่ใช่โยน error** เพราะหน้าแก้ต้องแสดงปัญหาทุกข้อพร้อมกัน ไม่ใช่ทีละข้อ
2. แต่ละปัญหาต้องบอก **path ที่ผิด** (เช่น `delter.process.cm.pressSpeed`) และบอกว่าผิดยังไง
3. ตรวจให้ครบตามที่เทส 16 ทำอยู่แล้ว
   - ทุกค่าของ field ที่เป็นช่วง normalize ได้ และ `min <= max`
   - ไม่มี `NaN` โผล่ที่ไหน
   - **ทุก key ในทุก patch ต้องอยู่ในชุด field ที่รู้จัก** ข้อนี้สำคัญที่สุด เพราะพิมพ์ชื่อ field ผิด (`steap` แทน `steep`) จะไม่มีอะไรจับได้เลยด้วยกลไกอื่น patch นั้นจะถูกเมินเงียบๆ และสูตรจะออกมาเหมือนไม่ได้เลือก process นั้น
   - ชุด field ที่รู้จัก: `temp`, `grind`, `steep`, `preinfusionWait`, `pressSpeed`, `restBetween`, `bypass`, `steepAdd`, `preinfusionAdd`, `pressSpeedAdd`, `tempClamp`, `note`
4. ตรวจเพิ่มจากเดิม
   - มี `version` และเป็นค่าที่เทียบกับ version อื่นได้
   - key ระดับเครื่องมีครบและมีแค่ `aeropress` กับ `delter`
   - ทุก combo ของ 4 ตัวแปร (2 × 3 × 8 × 3 × 6 = 864 ชุด) คำนวณผ่านโดยไม่โยน error และได้ค่าครบทุก field ที่การ์ดสูตรต้องใช้ ข้อนี้กันกรณีที่ v2 เคยเจอ คือค่าที่หายไปจาก base เพราะคิดว่ามีขั้นอื่นทับให้ครบแล้ว
5. รันได้ทั้งใน browser และใน node โดยไม่ต้องผ่าน bundler และไม่พึ่ง dependency ใดๆ
6. `brew.test.js` เดิมเปลี่ยนมาเรียกตัวนี้แทนที่จะตรวจเอง ผลลัพธ์ต้องเท่าเดิมหรือดีกว่า

## ต้องไม่ทำอะไร

- ไม่ตรวจว่าตัวเลขสมเหตุสมผลทางกาแฟไหม (อุณหภูมิ 200 องศาผ่านได้ นี่เป็นตัวตรวจรูปร่าง ไม่ใช่ตัวตรวจความรู้)
- ไม่แก้ค่าให้อัตโนมัติ ไม่เติมค่าที่ขาด รายงานอย่างเดียว
- ไม่พึ่ง schema library ตัวไหน ruleset มีรูปร่างเดียวที่รู้จักดีอยู่แล้ว เขียนตรงๆ สั้นกว่าและไม่ต้องแบก dependency เข้า Cloud Function

## จุดที่ต้องตัดสินตอน design

- `normalizeRange` ปัจจุบันโยน error พร้อม path อยู่แล้ว ตัวตรวจจะ reuse มันแบบจับ error หรือแยกตรรกะออกมา
- ตัวตรวจต้อง import `computeRecipe` เพื่อเดินครบ 864 combo ซึ่งทำให้ Cloud Function ต้องมี `brew.js` ไปด้วย ต้องตัดสินว่าจะแชร์ไฟล์ยังไงระหว่าง `src/` (bun/vite) กับ `functions/` (npm)
- ถ้าการเดิน 864 combo ช้าเกินไปสำหรับการตรวจสดตอนพิมพ์ในหน้าแก้ ให้แยกเป็นการตรวจ 2 ระดับ: ตรวจรูปร่างแบบเร็วตอนพิมพ์ ตรวจครบทุก combo ตอนกดเผยแพร่

## วัดผลยังไง

- ส่ง `brewing-rules.js` ปัจจุบันเข้าไป: ไม่มีปัญหาสักข้อ
- เปลี่ยน `steep` เป็น `steap` ที่ node หนึ่ง: รายงานปัญหาพร้อม path ที่ตรงจุด
- ใส่ `[150, 120]` (กลับหัว): รายงานว่า min มากกว่า max พร้อม path
- ลบ `pressSpeed` ออกจาก process หนึ่งของ Delter: รายงานว่ามี combo ที่ได้ค่าไม่ครบ
- ลบ `version`: รายงาน
- เพิ่มเครื่องที่สาม: รายงาน
- `bun run test` ผ่านทั้งชุดโดยที่จำนวนเทสไม่ลดลง
