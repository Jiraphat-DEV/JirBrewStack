# 12 · หน้าแก้ ruleset ของ admin และ Cloud Function

กลุ่ม: Rules · ต้องรอ: 09, 10 · ประมาณ 2.5 วัน
[กลับไป roadmap](../2026-08-05-jirbrewstack-v2.1-roadmap.md)

## ปัญหา

item 10 ทำให้แอปอ่าน ruleset จาก Firestore ได้แล้ว แต่ยังไม่มีอะไรเขียนมันเลย ต้องไปกดใน Firebase console ซึ่งไม่มีการตรวจอะไรทั้งนั้น เขียนพลาดทีเดียวแอปเพี้ยนพร้อมกันทุกคน

และตกลงกันแล้วว่า Firestore แทน Notion ทั้งหมด แปลว่าหน้านี้ต้องดีพอที่เจ้าของจะไม่กลับไปเปิด Notion อีก

item นี้เป็นตัวเดียวใน v2.1 ที่ต้องมี Cloud Function จริงๆ ที่เหลือ Firestore rules คุมได้หมด

## ต้องได้อะไร

1. **`functions/` พร้อม `package.json` ของตัวเองที่ใช้ npm** แยกจาก bun lockfile ของ repo เพราะ Cloud Build ของ Google ใช้ npm
2. **callable function `publishRuleset({ data })` ตัวเดียว** ทำ 4 อย่างตามลำดับ
   - เช็คว่า uid ของคนเรียกตรงกับ admin uid ที่ตั้งไว้ใน env ถ้าไม่ตรงปฏิเสธ
   - รัน `validateRuleset` (item 09) ถ้ามีปัญหา ปฏิเสธพร้อมคืนรายการปัญหาทั้งหมดพร้อม path **ไม่เขียนอะไรทั้งนั้น**
   - bump `version` ประทับ `updatedAt` และ `updatedBy`
   - เขียนทับ `rulesets/global`
3. การเช็ค admin อยู่ที่ function เท่านั้น **ห้ามมี field `role` ในฐานข้อมูล** เพราะ rules อนุญาตให้ผู้ใช้เขียน doc ตัวเองได้ ใครก็ตั้งตัวเองเป็น admin ได้ทันที
4. **หน้าแก้ในแอป** เห็นเฉพาะ admin เป็น textarea ที่ถือ ruleset ปัจจุบันเป็น JSON มีการตรวจสดตอนพิมพ์แสดงปัญหาพร้อม path และปุ่ม "เผยแพร่"
5. เผยแพร่สำเร็จแล้วแอปโหลด ruleset ใหม่ทันที ไม่ต้องรีเฟรช
6. เผยแพร่ไม่สำเร็จ: แสดงปัญหาทุกข้อ ไม่ใช่ข้อแรกข้อเดียว ค่าที่พิมพ์ค้างไว้ต้องไม่หาย
7. **`deploy.yml` เพิ่ม `functions` เข้า target** ตอนนี้จะเป็น `firebase deploy --only functions,firestore,hosting`
8. ก่อนเผยแพร่ต้องเห็นว่าจะเปลี่ยนอะไรบ้างเทียบกับตัวปัจจุบัน อย่างน้อยระดับ "มี N field ที่ต่างไป" ไม่ใช่กดแล้วทับเลย

## ต้องไม่ทำอะไร

- **ไม่ทำฟอร์มที่ generate ช่องกรอกตามโครง ruleset** ตาราง patch มีขนาด 2 เครื่อง × 3 roast × 8 process × 3 altitude × 6 origin ฟอร์มที่ครอบคลุมทั้งหมดเป็นงานหลายสัปดาห์เพื่อคนแก้คนเดียวที่เขียนไฟล์นี้ด้วยมือมาตลอดอยู่แล้ว textarea + ตัวตรวจที่ดีคือคำตอบที่ตรงกับความจริง ให้เขียน `ponytail:` กำกับไว้พร้อมทางอัปเกรด: ทำฟอร์มเฉพาะตาราง process ถ้าวันหนึ่งการแก้เริ่มเจ็บ
- ไม่เก็บประวัติเวอร์ชันของ ruleset ไม่มี rollback ในแอป (Firestore มี point-in-time recovery ให้อยู่แล้วบน Blaze และการกู้คือเรื่องที่เกิดปีละครั้ง)
- ไม่มี admin หลายคน ไม่มีหน้าจัดการสิทธิ์
- ไม่มี function อื่นนอกจากตัวนี้ ทุกอย่างที่เหลือใน v2.1 เป็น client + rules
- ไม่แก้ ruleset จากหน้าอื่นของแอป

## จุดที่ต้องตัดสินตอน design

- `validateRuleset` กับ `brew.js` ต้องรันได้ทั้งใน `src/` (vite/bun) และ `functions/` (npm) จะแชร์ไฟล์ยังไง ทางเลือกคือ copy ตอน build, symlink, หรือ workspace ทางที่เลือกต้องกันไม่ให้ทั้งสองฝั่งหลุดจากกันโดยไม่มีอะไรฟ้อง
- admin uid เก็บที่ไหน (env ของ function) และหน้าแก้ในแอปจะรู้ได้ยังไงว่าคนนี้เป็น admin เพื่อโชว์เมนู โดยที่การรู้ผิดไม่เป็นช่องโหว่ (function เป็นด่านจริง หน้าแอปเป็นแค่การซ่อนเมนู)
- region ของ function ควรตรงกับ region ของ Firestore
- ตัวตรวจสดตอนพิมพ์ควรใช้การตรวจแบบเร็ว (รูปร่างอย่างเดียว) ส่วนการเดิน 864 combo ทำตอนกดเผยแพร่ ตามที่ item 09 ทิ้งไว้ให้ตัดสิน
- JSON ใน textarea ตัวจริงต้องมาจาก ruleset ที่ใช้อยู่ ซึ่งอาจเป็นตัวจาก Firestore หรือ fallback ในโค้ด ต้องบอกให้ชัดว่ากำลังแก้ตัวไหน

## วัดผลยังไง

- admin เปิดหน้าแก้: เห็น ruleset ปัจจุบันเป็น JSON ที่อ่านได้
- ไม่ใช่ admin: ไม่เห็นเมนู และเรียก function ตรงๆ ก็ถูกปฏิเสธ
- ไม่ login แล้วเรียก function: ถูกปฏิเสธ
- แก้ `steep` เป็น `steap` แล้วกดเผยแพร่: ถูกปฏิเสธ พร้อม path ที่ผิด และ `rulesets/global` ไม่ถูกแตะ
- แก้อุณหภูมิถูกต้องแล้วเผยแพร่: `version` เพิ่ม แอปได้ค่าใหม่ทันที เปิดในเครื่องอื่นก็ได้ค่าใหม่
- เขียน JSON ผิดไวยากรณ์: บอกตรงจุด ค่าที่พิมพ์ไว้ไม่หาย
- deploy uat ด้วยมือ: function ขึ้นจริงและเรียกได้
