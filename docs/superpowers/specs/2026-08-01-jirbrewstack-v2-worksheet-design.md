## 2. หลักการที่ห้ามละเมิด

กฎเหล่านี้มาจาก Notion และเป็นเหตุผลที่โมเดลเดิมถูกทิ้ง ต้องสะท้อนอยู่ในผลลัพธ์ของแอป

1. **ค่าคงที่ของสองเครื่องแยกกันเด็ดขาด** ห้ามมี field ใดใช้ค่าร่วมกัน แม้ตัวเลขจะบังเอิญเท่ากัน (เช่น grind base 6.0 ทั้งคู่ ต้องเขียนแยกสองที่) เพราะ Notion สั่งไว้ว่า "Delter เป็นเอกเทศ ห้าม sync เลขกับหน้า AeroPress"
2. **ทิศทางความผิดพลาดของสองเครื่องกลับกัน** AeroPress = immersion เสี่ยงสกัดเกิน (ขม/ไม่มีกลิ่น) Delter = percolation เสี่ยงสกัดไม่พอ (บาง/เปรี้ยว) ตารางแก้รสจึงเรียงลำดับสลับกัน
3. **ห้ามลดการสกัดหลายทางพร้อมกัน** (เย็น + บาง + สั้น + หยาบ) กรอบเดิมพลาดตรงนี้ ผลลัพธ์ที่แอปคำนวณออกมาต้องไม่เกิดกรณีนี้
4. **Altitude ไม่แตะ temperature** แตะเฉพาะ grind (และ pre-infusion บน Delter) กฎเดิมที่ให้ altitude บวก temp ถูกถอดออกเพราะไปหักล้างส่วนลดของ fermented
5. **หน่วยบดเป็น Mavo Phantox Pro เท่านั้น** Timemore C2 เลิกใช้แล้ว C40 ไม่ได้มี ทั้งสองมีไว้แค่แปลงหน่วยตอนอ่านสูตรจากเน็ต
6. **ปัดค่า grind เป็นทวีคูณของ 0.5 เสมอ** เพราะ 1 C40 click = 2.7 Mavo clicks ค่าที่ละเอียดกว่านี้ไม่มีความหมาย

## 3. สถาปัตยกรรม

React 18 + Vite เหมือนเดิม ไม่เพิ่ม dependency ใดๆ (คงไว้ที่ `react` + `react-dom`) ไม่มี router state ทั้งหมดอยู่ใน `App.jsx`

```
App.jsx  ── state: device, roast, process, altitude, origin, view, recipe, picks
   │
   ├── Worksheet.jsx ── เลือกเครื่อง + 4 กลุ่มปุ่ม
   │     ├── RecipeCard.jsx ── การ์ดสูตร + slider เลือกค่าในช่วง + ปุ่ม "เริ่มชง"
   │     └── GrindConverter.jsx ── C40/C2 -> Mavo
   ├── Timer.jsx ── รับ steps จาก buildTimerSteps() + useWakeLock
   │     └── TimerStep.jsx
   └── FixTable.jsx ── ตารางแก้รส อ่านอย่างเดียว
```

Data flow เป็นทางเดียว: input 5 ช่อง → `computeRecipe()` → recipe object → RecipeCard แสดง + ให้เลือกค่าในช่วง → `buildTimerSteps(recipe, picks)` → Timer

## 4. โมเดลคำนวณ

### 4.1 Input

| ช่อง | ตัวเลือก |
|---|---|
| device | `aeropress` (inverted) · `delter` |
| roast | `agtron95plus` (95+ very light) · `agtron80_95` (80-95 light) · `agtron65_80` (65-80 medium) |
| process | `washed` · `honey` · `natural` · `anaerobic` · `cm` · `doubleAnaerobic` · `yeast` · `barrel` |
| altitude | `high` (>1,800) · `mid` (1,200-1,800) · `low` (<1,200) |
| origin | `ethiopia` · `kenya` · `colombia` · `brazil` · `panamaGeisha` · `thai` |

### 4.2 กติกาการรวมค่า

ทุก output ที่เป็นตัวเลขเก็บเป็นช่วง `[min, max]` เสมอ (ค่าเดี่ยวคือ `[n, n]`) ทำให้กติกาเดียวใช้ได้ทุก field

เริ่มจาก `base` แล้ว apply patch ตามลำดับ **roast → process → altitude → origin** (ลำดับเดียวกับขั้น 1-4 ใน worksheet) แต่ละ patch มีได้ 3 แบบ:

| แบบ | ความหมาย | ตัวอย่าง |
|---|---|---|
| `{ temp: [-6, -3] }` | delta บวกสะสมเข้าไปทั้งสองปลาย | `[88,88] + [-6,-3] = [82,85]` |
| `{ steep: [120, 150] }` (field ประเภททับ) | ทับค่าเดิมทั้งช่วง | steep กลายเป็น `[120,150]` |
| `{ steepAdd: 15 }` | บวกทีหลัง ใช้กับ altitude | `[120,150] -> [135,165]` |

field ประเภท **delta**: `temp`, `grind`
field ประเภท **ทับ**: `steep`, `preinfusionWait`, `pressSpeed`, `restBetween`, `bypass`
field ประเภท **บวกท้าย**: `steepAdd`, `preinfusionAdd`
field ประเภท **สะสมเป็น list**: `note` (string ต่อท้ายกัน แสดงใต้การ์ด)

`steepAdd` / `preinfusionAdd` สะสมรวมกันจากทุกขั้นแล้วบวกครั้งเดียวหลังสุด แปลว่าถ้าโดนสองขั้น (เช่น roast `agtron95plus` +15 และ altitude `high` +15) จะได้ +30

**ลำดับสำคัญกว่าที่คิด**: ทั้ง roast และ process ต่างก็ทับ `steep` ได้ เมื่อ process มาทีหลัง process จึงชนะ ซึ่งตรงกับที่ Notion แก้ไว้ว่าให้ attribute ของ process มาก่อน attribute ของ roast (เช่น medium + washed ได้ steep `[105,105]` ของ washed ไม่ใช่ `[105,135]` ของ medium)

หลัง apply ครบทั้ง 4 ขั้น:
1. clamp `temp` ให้อยู่ใน `tempCap` ของเครื่องนั้น (AeroPress `[80, 92]` · Delter `[85, 94]`)
2. ปัด `grind` ทั้งสองปลายเป็นทวีคูณของ 0.5
3. คำนวณ ratio ที่ derive ได้: `ratioConcentrate = water / dose`, `ratioFinal = (water + bypass) / dose` (คำนวณทั้งปลาย min และ max)

Origin ถูก apply เป็นขั้นสุดท้าย จึงชนะทุกขั้นก่อนหน้าในกรณีที่ใช้ค่าแบบทับ (มีที่เดียวคือ `panamaGeisha`)

### 4.5 การแปลงหน่วยบด

```
Mavo = C40_clicks * 0.271
Mavo = C2_clicks  * 0.320    // ความเชื่อถือต่ำ
```

ปัดผลลัพธ์เป็นทวีคูณของ 0.5 ช่อง C2 ต้องมีข้อความกำกับว่า "ใช้อ่านสูตรเก่าเท่านั้น ห้ามใช้ตั้งค่าจริง" เพราะ C2 มีช่วงใช้งานจริงแค่ ~36 คลิก (1 C2 click = 3.2 Mavo clicks) และการแปลงเทียบเฉพาะระยะห่างเฟือง ไม่ได้เทียบปริมาณผงละเอียด วัดจาก 23 สูตรที่ระบุทั้ง C2 และ C40 พบว่าเส้นทาง C2 ให้ค่าละเอียดกว่าเส้นทาง C40 เฉลี่ย 0.69 Mavo

## 5. UI

ภาษาไทยล้วน ใช้ธีมเดิม (design tokens ใน `index.css`, การ์ดมือถือกว้างสุด 480px ใน `App.css`)

### หน้า Worksheet

เลือกเครื่องด้านบน (2 ปุ่ม) ตามด้วย 4 กลุ่มปุ่มเรียงตามลำดับขั้น 1-4 ทุกช่องมีค่าตั้งต้น (`agtron80_95`, `washed`, `mid`, `colombia`) แปลว่าเปิดแอปมาก็เห็นสูตร base ทันที ไม่ต้องกดอะไรก่อน

ใต้ฟอร์มคือ **RecipeCard** แสดงสูตรที่คำนวณได้ ค่าที่เป็นช่วงจะมี `<input type="range">` ใต้ตัวเลข ให้เลื่อนเลือกก่อนกดเริ่มชง step ของ slider: temp 1°C, grind 0.5, เวลา 5 วิ, bypass 5 g

ค่าเริ่มต้นของ slider คำนวณแบบเดียวกันทุกช่อง: `min + floor((max − min) / 2 / step) * step` คือกลางช่วงปัดลงให้ลงตัวกับ step (เช่น `[40,60]` step 5 → 50 · `[105,120]` step 5 → 110 · `[20,25]` step 5 → 20) ค่าที่เลือกเก็บเป็น state ใน `App.jsx` (ไม่ persist) และรีเซ็ตกลับเป็นค่าเริ่มต้นใหม่ทุกครั้งที่ input 5 ช่องเปลี่ยน

การ์ดแสดง: กาแฟ, น้ำ (พร้อม ratio หัวเชื้อ), อุณหภูมิ, เบอร์บด Mavo (ทศนิยม เช่น "Mavo 6.0"), เวลาแช่ / pre-infusion + จังหวะกด, bypass (พร้อม ratio สุดท้าย), ฟิลเตอร์, อุณหภูมิตอนดื่ม, และ note ที่สะสมมาจากทั้ง 4 ขั้น

ท้ายหน้าคือ **GrindConverter** ช่องกรอกคลิก C40 หรือ C2 แล้วได้ Mavo

### หน้า Timer

`buildTimerSteps(recipe, picks)` สร้าง step จากค่าที่เลือกไว้

AeroPress:
1. ใส่กาแฟ เทน้ำถึง {water} g คนเบา 2-3 ที — 15 วิ
2. แช่ — {steep}
3. กลับด้าน กดช้าเบา — {pressDuration}
4. เติม bypass {bypass} g ชิมไปเติมไป — 20 วิ

Delter:
1. ใส่ผงกาแฟ เคาะข้างเครื่องให้หน้าผงเรียบ เทน้ำ {water} g ถึงขีด FILL — 20 วิ
2. Pre-infusion: ยกถึงขีด 50 กดจนสุด — 10 วิ
3. รอ — {preinfusionWait}
4. จังหวะ 1: ยกถึงขีด 75 กดช้าๆ — {pressSpeed}
5. พัก — {restBetween}
6. จังหวะ 2: ยกถึงขีด 75 (น้ำที่เหลือ) กดช้าๆ — {pressSpeed}
7. เติม bypass น้ำอุณหภูมิห้อง {bypass} g — 15 วิ

ระยะเวลาของ step ที่ worksheet ไม่ได้ระบุ (ขั้นเทน้ำ ขั้นเติม bypass ขั้นกด pre-infusion) เป็นค่าคงที่ที่ตั้งเอง เก็บไว้ใน `brewing-rules.js` พร้อมคอมเมนต์กำกับว่าไม่ได้มาจาก Notion

`useWakeLock` ขอ `navigator.wakeLock.request('screen')` ตอน timer เริ่มเดิน และ `release()` ตอนหยุด/ออกจากหน้า/unmount พร้อม re-acquire เมื่อ `visibilitychange` กลับมา visible (เบราว์เซอร์ปล่อย lock เองเมื่อสลับแท็บ) ถ้าเบราว์เซอร์ไม่รองรับให้เงียบไป ไม่ต้องแจ้ง error

## 6. Error handling

แอปไม่มี I/O ไม่มี network ไม่มี storage จึงไม่มี error path ที่มาจากภายนอก เหลือแค่:

- **input ที่เป็นไปไม่ได้**: ทุกช่องเป็นปุ่มจากรายการปิด และมีค่าตั้งต้นเสมอ จึงไม่มี state ที่ไม่ถูกต้อง `computeRecipe` โยน error ถ้าได้ key ที่ไม่รู้จัก (เป็นบั๊กโปรแกรม ไม่ใช่ input ผู้ใช้) และมีเทสคุม
- **Wake Lock ไม่รองรับ / ถูกปฏิเสธ**: จับ error แล้วเงียบ timer ทำงานต่อปกติ
- **GrindConverter รับค่าว่างหรือไม่ใช่ตัวเลข**: แสดงช่องผลลัพธ์เป็นว่าง ไม่แสดง NaN

## 7. Testing

`src/data/brew.test.js` รันด้วย `node --test` (เพิ่ม `"test": "node --test src/data/*.test.js"` ใน package.json) ไม่เพิ่ม dependency

เทสจับ `computeRecipe` ซึ่งเป็น pure function ทั้งหมด ไม่แตะ React เคสที่ต้องล็อก:

1. **base ตรงตาม Notion** — AeroPress `agtron80_95` + `washed` + `mid` + `colombia` → dose 18, water 190, temp 88, grind 6.0, steep 105 (washed ทับเป็น 1:45)
2. **ตาราง temp ทุกช่องตรง** — วนทุกคู่ (roast, process) ของทั้งสองเครื่อง เทียบกับตาราง "combo ที่พบบ่อย" ใน Notion ทั้ง 6 แถวต่อเครื่อง
3. **Delter สูงกว่า AeroPress 3°C ทุก combo** — วนทุกคู่ (roast, process) เทียบสองเครื่อง ต้องต่างกัน 3 พอดี (ยกเว้นแถว doubleAnaerobic ที่ offset ต่างกันโดยตั้งใจ: AeroPress −6..−3 vs Delter −5..−3 จึงเทียบเฉพาะปลาย max)
4. **เคสซ้อนหลายขั้น (steepAdd โดนสองรอบ)** — AeroPress + `agtron95plus` + `doubleAnaerobic` + `high` + `thai` → temp `[82, 85]`, grind `[5.0, 5.5]`, steep `[150, 180]` (process ทับเป็น `[120,150]` แล้วบวก steepAdd 15 จาก roast + 15 จาก altitude)
5. **Origin ชนะขั้นก่อนหน้า** — AeroPress + `panamaGeisha` ให้ temp `[85, 87]` แม้ process จะเป็น `washed` (ที่ปกติได้ 88)
6. **Process ชนะ Roast ในการทับ steep** — AeroPress + `agtron65_80` + `washed` ได้ steep `[105, 105]` ไม่ใช่ `[105, 135]`
7. **clamp tempCap ทำงาน** — สร้างกรณีที่ delta พาต่ำกว่า floor แล้วเช็คว่าถูก clamp
8. **grind ปัด 0.5 เสมอ** — วนทุก combo ที่เป็นไปได้ (3 roast × 8 process × 3 altitude × 6 origin × 2 เครื่อง = 864 กรณี) ยืนยันว่าทุกค่า `grind * 2` เป็นจำนวนเต็ม
9. **หลักการข้อ 3 ไม่ถูกละเมิด (เฉพาะ AeroPress)** — วนทุก combo ของ AeroPress ยืนยันว่าไม่มีกรณีไหนที่ temp ต่ำกว่า base พร้อมกับ steep สั้นกว่า base ในเวลาเดียวกัน (กฎ "เย็นแล้วต้องให้เวลามากขึ้น ไม่ใช่สั้นลง") — ไม่บังคับใช้กับ Delter เพราะแถว `doubleAnaerobic` ลดทั้ง temp และ pre-infusion และกดเร็วขึ้นพร้อมกันโดยตั้งใจ ตามที่ Notion เขียนว่าเป็น "แถวเดียวที่กดเร็วได้"
10. **`toMavo` ปัดถูก** — C40 22 → 6.0, C2 19 → 6.0, และผลลัพธ์ทุกค่าเป็นทวีคูณของ 0.5
11. **`buildTimerSteps` ใช้ค่าที่เลือกจริง** — AeroPress ได้ 4 step และ duration ของ step "แช่" เท่ากับค่า steep ที่ส่งเข้าไปพอดี · Delter ได้ 7 step โดย step "รอ" เท่ากับ preinfusionWait ที่ส่งเข้าไป และ step กดทั้งสองจังหวะเท่ากับ pressSpeed ที่ส่งเข้าไป

*(ไม่ assert เวลารวมเทียบกับ "เวลารวม" ใน Notion เพราะตัวเลขนั้นเป็นค่าประมาณที่ Notion เองไม่ได้บวกจาก step มาตรงๆ — บังคับให้ตรงจะเป็นการล็อกค่าคงที่ใน A5 ไว้กับตัวเลขที่ไม่แน่นอน)*

เทส 3, 8 และ 9 เป็นตัวคุมว่าถ้าใครไปแก้ตัวเลขใน `brewing-rules.js` แล้วทำหลักการพัง จะรู้ทันที ซึ่งเป็นจุดสำคัญเพราะไฟล์นั้นถูกออกแบบมาให้แก้บ่อย

ตรวจด้วยตาเพิ่ม: `bun run build` ต้องผ่าน และเปิดดูบนมือถือจริงหนึ่งรอบก่อนเปิด PR
